# コタロの大格闘 Online — Online Phase 3 完成報告

「GUEST 側 Client-side Prediction による操作遅延改善実験」。予測するのは GUEST が操作するルミポの LEFT / RIGHT / JUMP だけ。
HOST authoritative はそのまま（正しい状態は HOST が決め、GUEST が送るのは入力だけ）。攻撃・正式なオンライン対戦・rollback は実装していません。

## 1. 構造
```
GUEST                                                       HOST（正解）
 固定ステップ（60回/秒）ごとに入力を 1 件読む
   ├─ 入力番号をつけて HOST へ送る  ───────────────────▶  届いた順に並べ、1 ステップ 1 件ずつ
   └─ 同じ入力で「予測用ルミポ」を 1 ステップ進める           既存の Fighter.update() でルミポに適用
      → その場で画面に表示（次のフレーム）                    （HOST が使うのは入力だけ）
                                                             │
 HOST 状態が届く（30Hz）  ◀──────────────  a = 適用済みの入力番号 / p = ルミポの移動に関わる全ての値
   ├─ 番号 ≤ a の未確認入力を捨てる
   ├─ 予測用ルミポを p に置き換え、番号 > a の入力をもう一度順番に適用（reconciliation）
   └─ 作り直す前後の位置の差（予測誤差）は「表示のずれ」として残し、数フレームで消す
```
- 予測は表示のため（GUEST の画面だけ）。予測した位置を HOST へ送ることも、HOST が使うこともない。
- コタロは予測しない（Phase 2 と同じく HOST の状態を 70ms 遅らせて補間表示）。

## 2. 既存 Fighter 物理の再利用
- GUEST に「予測用ルミポ」を 1 体だけ作る：`new KG.Fighter(ルミポのキャラ定義, …)`。画面には描かず計算だけに使う。
- 1 ステップ進めるのは HOST と同じ `Fighter.update(1/60, コマンド, game.stage)`。加速・減速・最高速度・重力・ジャンプ・小ジャンプ・空中ジャンプ・コヨーテタイム・ジャンプバッファ・空中制御・床・一方通行床はすべて既存の処理。新しい物理は作っていない。
- コマンドの作り方も HOST と同じ関数（`RemoteInputController.toCmd`）を共用：`moveX = 右 − 左`、`held.jump`、`pressed.jump`（押した瞬間だけ）。
- 物理は足し算・掛け算・比較だけ（乱数・三角関数なし）で、ステージも静的なため、同じ値から同じ入力を与えれば HOST と GUEST で同じ結果になる。実測でも予測誤差はほぼ 0。
- ゲーム本体のファイル（Fighter・AI・物理・CPU 戦）は 1 行も変更していない。予測のコードは `online-move.js` の中だけで、操作実験の GUEST の時しか動かない。

## 3. 入力履歴（未確認入力）
- GUEST は毎ステップ 1 件 `{s: 番号, mx: -1/0/1, hj: 押しているか, pj: 押した瞬間か, t: 時刻}` を送り、同じものを「未確認入力」の列に入れる。
- 上限 180 件（3 秒分）。通常は Ping 分だけ（Ping 60ms なら 5〜8 件）。

## 4. HOST ack の利用
- HOST 状態の `a` は Phase 2 では「受信した最新番号」だったが、Phase 3 では「**ルミポに適用し終えた最新番号**」に変更。
- GUEST は状態が届くたびに、番号 ≤ a の未確認入力を捨てる（HOST で処理済み）。

## 5. Reconciliation
1. 状態の `p`（x, y, vx, vy, 向き, 接地, 空中ジャンプ残り, コヨーテ残り, ジャンプ先行入力残り, 技中のジャンプ保留, 小ジャンプ可, 吹っ飛び中）を予測用ルミポにそのまま設定（丸めない値）
2. 残っている未確認入力（番号 > a）を古い順に `Fighter.update()` で適用し直す
3. 作り直す前の予測位置との差 = 予測誤差
- HOST 側でルミポが場外・復帰待ちの時は予測を止めて HOST に従い、復帰した瞬間に HOST の位置から再開（誤差としては数えない）。

## 6. 補正（物理と表示を分ける）
- 物理（予測用ルミポの値）は常に「HOST の値 + 未確認入力」で正しく作り直す。誤差を消すために物理を加速・減速させることはしない。
- 画面の位置 = 予測位置 + 表示のずれ。作り直した瞬間に画面が飛ばないよう、差を「表示のずれ」に足し、時間で消す。

| 誤差（ゲーム内の座標。ルミポの幅 70、地上の最高速度 340/秒 ＝ 1 ステップ 約 5.7） | 扱い |
|---|---|
| 0.5 未満 | 補正として数えない（同じ方法で静かに吸収。見た目では分からない大きさ） |
| 0.5〜24（約 4 ステップ分の移動まで） | 小さい誤差：時定数 80ms で吸収（約 0.2 秒でほぼ消える） |
| 24〜120 | 大きい誤差：時定数 40ms で速めに吸収（約 0.1 秒） |
| 120 以上（約 21 ステップ分・体 1.7 個分） | 致命的：HOST 状態へ即座に合わせる（snap） |

- 確認：HOST 側でルミポを人為的に 8 / 60 / 300 ずらす → 8 と 60 は 1 フレームの移動が小さいまま滑らかに追従（snap なし）、300 は snap して HOST と一致。

## 7. ジャンプの予測
- JUMP を押した瞬間に予測用ルミポが既存のジャンプ処理でジャンプする（HOST の返事を待たない）。
- 押した瞬間は「回数」で送るので、HOST でも同じステップで 1 回だけ押した扱いになる → ジャンプバッファ・コヨーテタイム・空中ジャンプ（押した瞬間のみ）・小ジャンプ（早く離すと上昇を弱める）も HOST と同じ結果。
- HOST でジャンプが成立しなかった場合（例：HOST 側で状態が違った）は、次の状態で作り直されて HOST の結果に補正される。

## 8. 70ms 補間の変更
- ルミポ（予測 ON）：補間を使わない。予測位置をそのまま表示（入力した次のフレームから動く）。
- コタロ：Phase 2 と同じ 70ms 遅らせた補間。
- 予測 OFF：Phase 2 と同じ（ルミポもコタロも補間）。

## 9. HOST 側の変更（入力の扱い）
- Phase 2：入力が変わった時＋10Hz で送り、HOST は「最新の状態」を毎ステップ使う。
- Phase 3：GUEST の 1 ステップ = 1 件の入力を毎回送り（60Hz）、HOST は届いた順に 1 ステップ 1 件ずつ適用（予測と同じ順番になるため）。
  - 次の入力がまだ届いていない：直前の入力を続ける（押した瞬間は繰り返さない）。この時だけ予測と 1 ステップ分ずれる → 小さい誤差として補正される。
  - 未適用が 3 件を超えた（まとめて届いた）：そのステップで 1 件余分に適用して追いつく（HOST 側の遅れを約 50ms までに）。
  - 未適用の上限 30 件。
- 500ms 入力が届かなければニュートラル（Phase 2 のまま）。
- 通信量：GUEST → HOST 約 3.4KB/秒（60 件/秒）、HOST → GUEST 約 4.8KB/秒（状態 30Hz＋Ping）。

## 10. 予測の停止（通信が止まった時）
- 一番古い未確認入力が 500ms 以上 HOST に確認されない（入力が届いていない／HOST がニュートラルにした）間は、予測を止めて HOST の状態をそのまま表示する。自分の画面だけルミポが走り続けることはない。確認が戻れば自動で再開。
- 切断：操作実験が終わり、予測用ルミポも破棄（Phase 2 と同じ切断処理）。

## 11. 予測 ON / OFF（A/B 比較）
- GUEST の画面上部の「予測 ON / 予測 OFF」ボタン、または **P キー**で、実験中いつでも切り替えられる。
- 切り替えた瞬間は表示位置がつながるように 0.4 秒かけて移る（移動中に切り替えても飛ばない）。
- 選んだ設定は次の操作実験でもそのまま。URL に `?pred=off` を付けると最初から OFF。
- OFF は Phase 2 と同じ表示（HOST 状態の補間）。通信・HOST の処理は ON / OFF で同じなので、表示の違いだけを比べられる。

## 12. 診断表示（GUEST）
- 予測 ON / OFF、PING、入力送信 Hz、HOST 状態受信 Hz、last input seq、HOST ack、未確認入力数
- 予測誤差 X / Y（最新）、平均、最大、0 でなかった回数 / 作り直し回数、補正回数、snap 回数、表示のずれ、予測停止
- 入力→HOST で反映→受信、体感の目安（ON：ルミポ 次のフレーム／コタロ 何 ms 遅れ）
- HOST 側：受信 / 適用済み番号、未適用の入力数、届く前に続けた回数、追いつき回数

## 13. 入力から画面までの遅延（構造）
| | 経路 | 目安 |
|---|---|---|
| Phase 2（予測 OFF と同じ） | 入力 → HOST → 物理 → 状態送信 → 70ms 補間 → 表示 | **Ping + 約 110ms**（Ping 57ms なら約 170ms） |
| Phase 3（予測 ON）のルミポ | 入力 → 次の固定ステップで予測 → そのフレームで表示 | **約 0〜17ms（1 フレーム以内）。Ping に関係しない** |
| Phase 3 のコタロ（遠隔） | HOST の状態 → 70ms 補間 | Ping/2 + 約 80〜100ms 遅れて表示（Phase 2 と同じ） |

### 人工遅延での実測（同一 PC。押してから GUEST 画面のルミポが反応するまで、ms。平均 / 最大）
| 条件 | ON 動き出し | ON 離す | ON 切り返し | ON ジャンプ | OFF 動き出し | OFF ジャンプ |
|---|---|---|---|---|---|---|
| Ping 約 30ms | 11 / 19 | 21 / 43 | 9 / 15 | 8 / 18 | 131 / 152 | 180 / 323 |
| Ping 約 60ms | 16 / 21 | 22 / 57 | 15 / 20 | 14 / 20 | 171 / 182 | 216 / 330 |
| Ping 約 100ms | 11 / 18 | 24 / 54 | 9 / 15 | 15 / 29 | 200 / 210 | 341 / 521 |
| Ping 約 200ms | 15 / 23 | 24 / 36 | 17 / 27 | 10 / 18 | 299 / 306 | 316 / 323 |
| 揺れ 40→70→50→100→45ms＋時々の遅延 | 18 / 24 | 26 / 69 | 16 / 24 | 11 / 20 | 150 / 174 | 196 / 300 |
- 「離す」「切り返し」は 1 フレームの移動量が 1 割以上落ちた時点で計測（減速は物理どおりなので 1〜2 フレーム）。OFF の離す・切り返しは補間の速度変化と区別しにくいため表から除外。
- 計測はブラウザの描画タイミング（60fps）込み。ON はどの Ping でも 1〜2 フレーム、OFF は Ping に比例して増える。

### 予測誤差・補正（各条件 約 25 秒：長押し・停止・短押し・細かい切り返し・ジャンプ・小ジャンプ・空中ジャンプ・走りながらジャンプ）
| 条件 | 平均誤差 | 最大誤差 | 0 でない / 作り直し | 補正 | snap | HOST が届く前に続けた回数 | 画面の震え | 最後の位置の差 |
|---|---|---|---|---|---|---|---|---|
| Ping 約 30ms | 0.00 | 6.3 | 4 / 748 | 4 | 0 | 4 | 0 | 0.0 |
| Ping 約 60ms | 0.00 | 5.7 | 3 / 747 | 2 | 0 | 5 | 0 | 0.0 |
| Ping 約 100ms | 0.00 | 9.0 | 5 / 747 | 5 | 0 | 9 | 0 | 0.0 |
| Ping 約 200ms | 0.00 | 12.6 | 8 / 753 | 8 | 0 | 15 | 0 | 0.0 |
| 揺れ＋時々の遅延 | 0.25 | 21.4 | 48 / 736 | 48 | 0 | 81 | 0 | 0.0 |
- 誤差が出るのは「HOST で次の入力が間に合わなかった」時だけ（1 回あたり 1 ステップ分 ≒ 5.7）。すべて小さい誤差の範囲で、snap は 0。
- 移動中に予測 ON / OFF を切り替えた時の 1 フレームの最大移動：11〜18（通常の走り 5.7 の 2〜3 倍程度で、0.4 秒かけてつながる）。

## 14. スマホ
- GUEST のパッド（LEFT / RIGHT / JUMP）もキーボードと同じ入力の流れなので、タッチした次のフレームで予測に反映。
- 確認：LEFT タッチ → 3〜6ms、LEFT を押したまま JUMP → 約 18ms、指を RIGHT へ滑らせる → 約 17ms で向きが変わる。終了後に HOST と GUEST の位置が一致。
